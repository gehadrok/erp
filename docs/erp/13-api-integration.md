# 13. واجهات API والتكامل

## 13.1 مبادئ الواجهة

- REST بتنسيق JSON، مسارات بحالة `kebab-case`، حقول `camelCase`.
- إصدار في المسار: `/api/v1/...`.
- كل الطلبات تحمل رمز المصادقة (Bearer JWT) وتعمل في سياق شركة (من الجلسة/التوكن، وليس من معامل).
- الاستجابة الموحدة:

```json
// نجاح
{ "data": { ... }, "meta": { "page": 1, "pageSize": 25, "total": 143 } }
// خطأ
{ "error": { "code": "ENTRY_NOT_BALANCED", "message": "القيد غير متوازن: مدين 1200 دائن 1100", "details": [ ... ] } }
```

- أكواد خطأ ثابتة تُوثق (ENTRY_NOT_BALANCED, PERIOD_CLOSED, CREDIT_LIMIT_EXCEEDED, INSUFFICIENT_STOCK, ...).

## 13.2 نقاط النهاية الرئيسية

```
POST /api/v1/journal-entries            إنشاء قيد (مسودة)
POST /api/v1/journal-entries/{id}/approve
POST /api/v1/journal-entries/{id}/post
POST /api/v1/journal-entries/{id}/reverse

POST /api/v1/sales-invoices             إنشاء فاتورة (مسودة)
POST /api/v1/sales-invoices/{id}/confirm   ← يشغّل: مخزون + قيد + فاتورة إلكترونية
POST /api/v1/sales-invoices/{id}/cancel

GET  /api/v1/reports/trial-balance?from=2026-01&to=2026-09&branchId=
GET  /api/v1/accounts/{id}/statement?from=&to=

GET/POST /api/v1/customers, vendors, items, warehouses
POST /api/v1/receipts, /api/v1/payments (مع allocations)
```

**قواعد الحالة:** كل مستند له مسودة → تأكيد؛ التأكيد عملية ذرية (معاملة واحدة)؛ الإلغاء بعد التأكيد يمر بمستند معاكس (لا حذف).

## 13.3 المعاملات والتزامن

- **Idempotency-Key** (رأس إلزامي للعمليات المالية) — نفس المفتاح لا ينفذ مرتين (جدول `idempotency_keys` يخزن نتيجة أول تنفيذ 24 ساعة).
- **قفل تفاؤلي** بعمود `version` على المستندات؛ تعارض → 409 مع نسخة حالية.
- **الترقيم**: زيادة ذرية على `sequences` (UPDATE ... RETURNING) — لا فجوات بمعنى الرقم مضمون التفرد، والفجوة مقبولة عند الفشل.
- **المخزون**: تحديث `stock_balances` داخل نفس المعاملة؛ تحت ضغط عالٍ تستخدم `SELECT ... FOR UPDATE` على صف الصنف/المستودع (صف واحد لكل صنف — بلا ميتلوك إذا روعي ترتيب معرّف الصنف).

## 13.4 الأداء

- فهرسة: القيود (date, status)، الأسطر (account_id)، الحركات (item_id, warehouse_id).
- التقارير الثقيلة (أكبر من 2 ثانية) تنفذ على replica للقراءة أو عبر الطابور.
- تخزين مؤقت لقوائم القراءة فقط (ETag / Redis 30-60 ثانية).
- تحديد معدل (rate limit) لكل مستخدم: 120 طلب/دقيقة.

## 13.5 التكاملات

| التكامل | الاتجاه | الطريقة |
|---------|---------|---------|
| بوابة الفاتورة الإلكترونية | صادر | REST + توقيع رقمي + طابور retry |
| البنوك (كشوف الحسابات/المدفوعات) | صادر/وارد | استيراد كشف (Camt.053/CSV) ومطابقة تلقائية مع السندات |
| أجهزة نقاط البيع POS | وارد | API: فاتورة مبسطة لحظية + مزامنة المخزون |
| بريد/SMS | صادر | تنبيهات تحصيل، إرسال الفواتير للعملاء |
| أنظمة خارجية (متاجر إلكترونية) | وارد | Webhook + تحقق توقيع، جدولة استيراد الطلبات |
| استيراد/تصدير Excel | كلاهما | استيراد بأي جداول (عملاء، أصناف، أرصدة افتتاحية) مع تحقق |

### مطابقة كشف البنك
1. استيراد الكشف (كشف بنكي: تاريخ، وصف، مبلغ، مرجع).
2. مطابقة تلقائية بالمبلغ + المرجع/التاريخ (ضمن نطاق تسامح).
3. ما لا يُطابق تلقائياً يُعرض لمطابقة يدوية؛ الفروق تُرحّل لمصروف/إيراد مناسب.
4. تقرير مطابقة بنكية بحالة كل سطر.

## 13.6 Webhooks صادرة

```
invoice.confirmed, invoice.einvoice.accepted, receipt.created,
payment.created, stock.low, period.closed
```
- التسجيل من الإعدادات (URL + سر للتوقيع HMAC-SHA256 في رأس `X-Signature`)، إعادة محاولة 5 مرات بتراجع أسي.
