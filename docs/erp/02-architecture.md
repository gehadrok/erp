# 2. المعمارية والتقنيات

## 2.1 المعمارية الكلية

نظام موحّد (Modular Monolith) بواجهات متعددة:

```
┌─────────────────────────────────────────────────────────┐
│                    العملاء (Clients)                     │
│  Web App (React)   │  Desktop (اختياري)  │  Mobile       │
└────────────────────────────┬────────────────────────────┘
                             │ HTTPS / REST + WebSocket
┌────────────────────────────▼────────────────────────────┐
│                    API Gateway / Nginx                   │
└────────────────────────────┬────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────┐
│                ERP Core (Modular Monolith)               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ Core/    │ │ GL Engine│ │ Inventory│ │ AP/AR    │    │
│  │ Settings │ │ (قيود)   │ │ (مخازن)  │ │(مبيعات/  │    │
│  │          │ │          │ │          │ │ مشتريات) │    │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ Payroll  │ │ Assets   │ │ Tax &    │ │ Reports  │    │
│  │          │ │          │ │ EInvoice │ │          │    │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘    │
│  ┌──────────────────────────────────────────────────┐   │
│  │       Shared: Auth, Audit, Sequences, i18n       │   │
│  └──────────────────────────────────────────────────┘   │
└──────┬───────────────┬───────────────┬──────────────────┘
       │               │               │
┌──────▼─────┐  ┌──────▼─────┐  ┌──────▼─────────────┐
│ PostgreSQL │  │ Redis      │  │ Worker/Queue       │
│ (المصدر    │  │ (Cache,    │  │ (تقارير ثقيلة،     │
│  الرئيسي)  │  │  Sessions) │  │  إرسال فواتير إلكترونية، إيميلات) │
└────────────┘  └────────────┘  └────────────────────┘
```

**لماذا Modular Monolith وليس Microservices؟**
- أنظمة المحاسبة تحتاج معاملات ACID عبر وحدات متعددة (فاتورة → مخزون → قيد في نفس المعاملة).
- Microservices تعقّد الضمانات المالية دون حاجة حقيقية في هذه المرحلة.
- الوحدات تفصل منطقياً داخل نفس العملية ويمكن استخراج خدمة لاحقاً عند الحاجة.

## 2.2 التقنيات المقترحة

| الطبقة | الخيار الموصى به | البديل |
|--------|------------------|--------|
| Backend | .NET 8 (C#) + EF Core | NestJS + TypeORM / Django + DRF |
| قاعدة البيانات | PostgreSQL 16 | SQL Server |
| Cache/Queue | Redis + BullMQ (أو Hangfire لو .NET) | RabbitMQ |
| Frontend | React 18 + TypeScript + Ant Design | Vue 3 + Element Plus |
| Reporting | استعلامات SQL مباشرة + قوالب JSON | JasperReports / SSRS |
| المزامنة مع بوابة الضريبة | Queue + retry + توقيع رقمي | — |
| النسخ الاحتياطي | pg_dump يومي + WAL archiving | — |

**معايير الاختيار:** فريق صغير، الحاجة لمعاملات مالية صارمة، توفر مهارات محلية، تكلفة التشغيل.

## 2.3 الوحدات الداخلية وحدودها

كل وحدة مجلد مستقل مع منطقها ومخططاتها:

```
/src
  /modules
    /core          # الشركات، الفروع، العملات، الترقيم، الإعدادات
    /gl            # دليل الحسابات، القيود، الفترات، الإقفال
    /inventory     # الأصناف، المستودعات، الحركات، التكلفة
    /purchasing    # الموردون، أوامر الشراء، فواتير الشراء، الدفعات
    /sales         # العملاء، الفواتير، المرتجعات، التحصيل
    /cash          # صناديق وبنوك، شيكات، تحويلات
    /payroll       # الهيكل الوظيفي، المسير، البدلات
    /assets        # الأصول الثابتة والإهلاك
    /tax           # الإعدادات الضريبية، الإقرارات
    /einvoice      # التوليد والتوقيع والإرسال
    /reports       # ميزان، قوائم مالية، تقارير تشغيلية
    /auth          # مستخدمون، أدوار، صلاحيات
    /audit         # سجل التدقيق
  /shared          # DTOs مشتركة، أدوات، ثوابت
  /jobs            # مهام مجدولة (إهلاك شهري، أسعار صرف، نسخ احتياطي)
```

**قاعدة الفصل:** الوحدة لا تلمس جداول وحدة أخرى مباشرة؛ تمر عبر خدمة الوحدة أو أحداث داخلية (In-process events).

## 2.4 تدفق مستند نموذجي (فاتورة بيع)

```
عرض سعر (اختياري)
   └─► فاتورة بيع ──► حركة مخزنية (صرف بالتكلفة) ──► قيد محاسبي
              │                                            │
              └──► مستند ضريبي (فاتورة إلكترونية)          └──► أرصدة لحظية
              └──► رصيد عميل (ذمم مدينة)
```

كل خطوة في **معاملة DB واحدة**: إما تكتمل جميعها أو يفشل المستند كله.

## 2.5 بيئات التشغيل

| البيئة | الغرض | البيانات |
|--------|-------|----------|
| `dev` | تطوير محلي | بيانات وهمية |
| `staging` | اختبار قبول + اختبار الربط مع بوابة الضريبة (بيئة اختبار رسمية) | نسخة مُجهّلة من الإنتاج |
| `prod` | التشغيل الفعلي | بيانات حقيقية |

## 2.6 استراتيجية النشر

- Docker + docker-compose للتطوير، Kubernetes أو Docker Swarm للإنتاج الصغير.
- نشر أزرق-أخضر بسيط: نسختان من التطبيق مع تبديل Nginx.
- الهجرات (migrations) تُطبق قبل التشغيل عبر خط نشر مؤتمت، وتكون **متوافقة للخلف** (backward compatible) حتى تكتمل الترقية.

## 2.7 استراتيجية الاختبار

| النوع | النطاق | الأدوات |
|-------|--------|---------|
| Unit | منطق القيود والتكلفة والضرائب | xUnit / Jest |
| Integration | مستند كامل + قيد + حركة مخزنية | Testcontainers (Postgres حقيقي) |
| E2E | سيناريوهات دورة كاملة (شراء→بيع→تحصيل) | Playwright |
| Performance | ترحيل دفعات قيود، تقارير كبيرة | k6 |

**اختبارات محاسبية ذهبية (يجب أن تُكتب أولاً):**
1. قيد غير متوازن يُرفض.
2. فاتورة بيع تُنتج قيداً بصيغة (مدين: العميل، دائن: المبيعات + ضريبة).
3. متوسط مرجح: 3 عمليات شراء بأسعار مختلفة ثم بيع — تحقق من التكلفة.
4. عكس قيد مرحّل لا يغيّر الأصل.
5. إقفال فترة يمنع أي ترحيل إليها.
